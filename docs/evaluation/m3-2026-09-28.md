# M3 development and evaluation

Recorded on 2026-09-28. M3 implementation and its required per-rule precision
and usage-noise reports are complete. All nine new rules remain preview.
The results below do not support promoting any of them. Local checks passed;
the standard Linux CI performance gate has not been rerun for this change.

## Delivered behavior

The [section classifier](../reference/sections.md) exposes source-bound roles
and evidence through the library and `parse` JSON. It covers steps, reference,
rationale, background, troubleshooting, and unclassified content. Classification
does not change kind resolution or cached parse facts.

The rule registry implements STL002, STL004, RAT001, ORD001, ORD002, MIX001,
VOX002, VOX003, and EVD001. Each has executable positive/negative documentation
examples and a diagnostic snapshot. Kind scopes, preview selection, language
selection, and suppression use the existing engine. Semantic suggestions have
no automatic edits. MIX001 initially reports extended rationale in procedural
or reference pages; it does not detect every possible responsibility conflict.

The [evaluation procedure](../../corpus/docs/evaluation.md#heuristic-evaluation)
provides commands for tuning, freezing, labeling, section audits, and real
edit-history replay. The manual Evaluation workflow now records section
predictions and replays Git document changes alongside ecosystem and latency
checks.

## Tuning and threshold calibration

The [first tuning run](../../corpus/results/m3/tuning-v1/run.json) produced five
new diagnoses. [Individual review](../../corpus/results/m3/tuning-v1/labels.json)
identified four false positives and one uncertain comparison. Corrections
excluded durable license names and historical fixes, removed a plural project
voice marker, and required an action at the start of an ordered procedure.
The [second tuning run](../../corpus/results/m3/tuning-v2/run.json) retained only
the uncertain comparison. These corrections preceded holdout inspection.

The [threshold decision](../../corpus/results/m3/calibration-v1/decision.json)
retains existing duplicate-rule defaults. Eleven one-factor candidates covered
identifier count, Jaccard similarity, paragraph similarity, paragraph length,
and shingle size on 1,291 tuning documents. All produced zero DUP/OWN diagnoses
under the frozen kind profiles. Those observations cannot distinguish candidate
precision and do not justify changing a default. Complete candidate results
remain in the bound compressed report beside the decision.

## Natural precision

The [frozen natural run](../../corpus/results/m3/natural-v1/run.json) covers the
same 1,953 pinned documents and Git inventories as M2. Reversing source,
document, and inventory order produces identical bytes. The
[ecosystem comparison](../../corpus/results/m3/ecosystem-v1/changes.json) preserves
all 4,480 existing diagnostic objects and adds 11 new ones.

All new diagnostics received individual source-context review by the authoring
agent. [Labels](../../corpus/results/m3/natural-v1/labels.json) and the
[summary](../../corpus/results/m3/summary.json) bind judgments to input and

Tuning has one uncertain EVD001 diagnosis and no other new diagnoses. The
summary retains every rule's tuning/holdout, language, and kind groups,
including empty groups. The frozen kind profiles leave 1,734 documents with
unknown kinds; those documents cannot exercise kind-dependent heuristics.
Zero samples establish neither precision nor recall.

The holdout reveals concrete limitations: MDX tabs can hide early commands;
JSON, YAML, inline commands, and JavaScript examples can already supply the
main flow; Japanese behavior enumerations can resemble procedures. Version
bounds phrased as “prior to” or “or higher” are missed. Example assistant
output can resemble a live deployment assertion. Useful procedural
recommendations and same-paragraph conceptual justifications can fail EVD001's
measurement/link test. No rule or threshold changed in response to these
holdout findings.

## Section audit

The [section audit](../../corpus/results/m3/sections-v1/summary.json) reviews
38 sections sampled from 15,918 nonempty headed sections, across tuning and
holdout, English, Chinese, Japanese, and all six predicted roles. Selection
includes unclassified sections and a type-independent hash sample.

Eighteen predicted roles match the reviewed dominant responsibility. Nine
unclassified sections contain a missed responsibility. Other mismatches include
console output treated as steps, ordinary alternative-client links treated as
rationale, and instructional API examples assigned from heading words alone.
Every label retains its reason and source binding. This stratified audit is
not a population accuracy or rule-recall estimate.

## Edit-history usage noise

The [accepted replay](../../corpus/results/m3/history-v3/run.json) covers 155
real Markdown path changes through `cc93e11`, using complete first-parent Git
history. It stores original before/after content, commit identities, complete
diagnostics, and newly introduced warnings. Position-only movement does not create a new warning; persistent warnings
still count toward blocking on every checked change. Rules and input order were checked for equivalence.

The replay contains 26 post-change diagnoses, all false positives. EVD001,
VOX002, and VOX003 each incorrectly block six of 155 changes: 3.87 blocks per
100 changes. STL004 blocks one change: 0.65 per 100 changes. The other five
rules have zero incorrect blocks. Multiple false diagnoses on the same change
count once per rule, and all clean changes remain in the denominator.

Six of those diagnoses are newly introduced; the others persist across edits.
The earlier [introduced-only summary](../../corpus/results/m3/introduced-only-summary.json)
is retained as a superseded metric. Counting only newly introduced warnings
understates interruption frequency, so the accepted summary uses all
post-change diagnostics.

This is a simulation with preview enabled, under one fixed kind profile,
not observed user interruptions. It covers one repository and does not
reconstruct historical configuration. The early untyped design proposal falls
back to reference under that profile, causing a non-goals false positive.
Other noise comes from quoted detector examples in tables and version syntax
examples introduced by “such as”.

The [initial replay](../../corpus/results/m3/history-v1/run.json) is preserved.
It omitted the current release-note kind mapping and produced one additional
version diagnosis. The second run corrects only that replay profile. The third run adds complete
post-change diagnostic labeling for the blocking metric. Natural corpus kinds
and rule behavior are unchanged; all runs retain their labels.

## Repairs and local verification

[Authored repair regressions](../../tests/repairs.rs) exercise all nine new
rules together, require the repaired examples to pass, and preserve unaffected
identifiers, links, and numbers. These fixtures do not establish independent
agent comprehension or human-reviewed meaning preservation. Those promotion
evaluations have not been performed.

Local Windows verification passed 212 Rust tests and 137 Python tests.
Two opt-in Rust corpus tests remain outside the routine suite. Rustfmt and
strict Clippy passed. Rule documentation examples, source ranges through
entities and Unicode, cache modes, preview/kind/language scope, suppression,
classifier misses, and repair examples have regression coverage. The repository's
stable check passes. Its preview check retains three existing diagnoses:
one historical-revision pointer under STL003 and two catalog-directory pointers
under PTR002. Their source lines are unchanged from the base revision; the new
M3 rules report no diagnoses on the final repository documentation.

The [local performance result](../../corpus/results/m3/performance/local-windows.json)
uses the canonical 1,000-file workload with five samples per mode. Median cold,
warm, and hook times are 513 ms, 92 ms, and 34 ms. Cache modes and hook scope
produce equivalent output. This local Windows result does not satisfy the
standard Linux CI acceptance gate; the manual workflow retains that gate.

The [revalidation](../../corpus/results/m3/revalidation.json) requires identical
natural, section, and history results from the final implementation after
editing rule-help prose. The
[verification receipt](../../corpus/results/m3/verification.json) binds the test
sources, evaluator scripts, and reports checked here.
