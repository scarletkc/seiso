# OWN002: Ambiguous content ownership

## What it checks

Reports directly matching content whose highest-ranked owners are tied.
Both canonical documents tie even if their kinds differ. Without canonical
declarations, the normal ownership ordering applies.

## Basis

Heuristic. Repeated content needs an explicit owner when document roles do not resolve it.

## Why it matters

Two equally authoritative definitions leave maintainers unsure which one to update.

## Example

In `guide.md`, when another reference page defines the same settings:

```markdown
---
kind: reference
---

- `host`: Server address.
- `port`: Listening port.
- `user`: Account name.
- `token`: Access token.
- `timeout`: Request timeout.
```

## Instead

```markdown
---
kind: reference
---

See [the settings reference](reference.md#settings).
```

## Exceptions

Generated files can own content but receive no diagnostics. A block with a
directly matching higher-ranked owner is not a highest-rank tie. Connections
through a third block do not establish a match between two other blocks.
Invalid frontmatter cannot grant canonical ownership.

## Inputs

The pairwise definition, restatement, and prose comparisons used by the DUP
rules, even if those diagnostic codes are disabled, ranked by the
[ownership precedence](../reference/convention.md#ownership-precedence). Each
tied block reports its directly matching tied peers in `related`.

## Configuration

Enable preview and select `OWN002`. Duplication thresholds come from
`[lint.dup]`. A single authoritative file can declare `canonical: true`;
declaring it in both files preserves the ambiguity.
