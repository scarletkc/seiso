# LNK002: Missing local link anchor

## What it checks

Reports a fragment that is confirmed absent from an indexed Markdown target.
The target's headings, repeated-heading suffixes, and explicit HTML `id` or
anchor `name` attributes contribute anchors. A trailing heading attribute list,
such as `{#install}` or `{: #install .note}`, contributes its ids and the slug
of the heading text before it.

## Basis

Consistency. A document link must identify an existing destination.

## Why it matters

Renaming a heading can break incoming links while leaving the file in place.
The diagnostic includes the target so checking that changed file also reports
the broken incoming link.

## Example

In `guide.md`, with `reference.md` containing a heading named `Settings`:

```markdown
---
kind: howto
---

Read [the settings](reference.md#removed).
```

## Instead

```markdown
---
kind: howto
---

Read [the settings](reference.md#settings).
```

## Exceptions

External URLs and empty fragments are outside this check. Missing files belong
to `LNK001`. Anchors in excluded or non-Markdown files remain undetermined;
their suppressions cannot be declared stale. Generated Markdown is indexed
and can supply valid anchors.

## Inputs

Parsed links, the current workspace inventory, and indexed anchor spans.
Relative paths resolve from the source file; leading `/` uses the workspace root.
In a documentation site, a link resolves to a route's page source as `LNK001`
describes, and its fragment is checked in that page.
Percent-encoded fragments are decoded before exact comparison.

## Configuration

Enable preview and select `LNK002` through `[lint]`. Anchor generation follows
GitHub heading conventions; site-specific slug rewrites require suppression
with the renderer's behavior as the reason.
